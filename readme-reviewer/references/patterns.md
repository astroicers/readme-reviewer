# 高低品質樣態速查

> 來源:公開規範(**待查證**,見 rubric.yaml 的 `triangulation_sources`)+
> 姊妹專案 `skill-quality-research` 54 份質化筆記收斂的寫作工藝樣態。
> **不是**星數梯度歸納 —— 這裡沒有「這樣做會更受歡迎」的宣稱。

| 維度 | 高品質樣態 | 反例 |
|---|---|---|
| **R-001 第一屏** | 標題後一句話說清「是什麼 + 給誰」;有與替代方案的差別 | badge 牆把定位擠掉;標題只有專案名且下方直接進安裝;第一段講作者心路歷程;只有抽象形容詞(「強大」「優雅」) |
| **R-002 最短路徑** | 前置條件明說(語言版本/OS/金鑰);指令可直接貼;**附預期輸出**讓人知道有沒有裝對 | 隱含前置條件(要 Docker 卻沒說);只有 `npm install` 沒有「然後呢」;佔位符沒說去哪拿 |
| **R-003 寫作品質** | 關鍵選擇附**因果理由**;有輸出樣張/比較表/可證偽判別法;before-after 對照 | 整份只有功能清單零個例子;「支援 X」但沒有一行 X 的用法;changelog 侵入正文 |
| **R-004 限制誠實** | 有非目標(non-goals)/已知限制/適用邊界;易腐內容帶**時效或驗證方式** | 效能數字無來源無日期;宣稱支援 N 種平台而零實測痕跡;文件描述與程式碼已不一致 |

## 形狀誤判速查(最常見的誤判來源)

| 看到 | 不要直接判 | 先查 |
|---|---|---|
| 沒有安裝指令 | R-002 poor | 是不是 **library/研究/awesome** 形狀 → 可能 `n/a` |
| 根 README 很薄 | R-001 poor | 是不是 **monorepo** → 以子套件抽樣 |
| 沒有「什麼時候別用」 | R-004 poor | **有沒有易腐內容** → 沒有的話是 `n/a` 不是 poor |
| H1 等於 repo 名 | R-001 扣分 | 定位句可能在**下一行** —— 這是 GitHub 慣例,見 misjudgments.md |

## 安全樣態(標示 ≠ 禁止)

| 樣態 | 讀法 |
|---|---|
| `curl … \| sh` | **慣例,不是罪。** 判的是有沒有並列非管道路徑、有沒有讓人先看腳本 |
| 範例含高熵 token | 佔位符(`<YOUR_TOKEN>`)不算;真的像憑證的才算 |
| 「照輸出逐字執行」 | ⚠️ **極性反轉是具名前科**:「**不要**照著執行」會被正向 marker 誤中。命中一律低信心 |
